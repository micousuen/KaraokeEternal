System Architecture

Karaoke Eternal · high-level design with section diagrams · updated 2026-08-13

At the highest level, Karaoke Eternal is one self-hosted Node.js service, one browser application used in different roles, one SQLite database, and a set of bounded background workers around a media library on disk.

Companion document: Runtime Configuration Design.

1. System context

Phones select and queue songs; an administrator manages the room and library; one browser claims the room's active-player role and renders audio/video. All use the same React application and connect to the same server.

7. Automatic media-processing policy

Processing starts only when it produces a user-visible output. Separation is a preparation step for scripting or instrumental generation, never a standalone automatic task.

If a dual-track classifier cannot decide during automatic processing, the job is skipped instead of guessing A1. Forced regeneration may explicitly fall back to A1.

13. Intentional boundaries

Single server instancePlayer claims, socket presence, request idempotency, queue operation lanes, and in-memory job registries are process-local. Horizontal scaling requires shared coordination before multiple server instances are safe.
Filesystem is part of the modelThe database identifies media, but source bytes and SRT sidecars remain authoritative on disk. Paths must be stable and writable for generated outputs.
Browser capability winsThe server avoids universal pre-transcoding. It adapts only when a player reports that a source stream or separate-stream playback is unsupported.
Background work is recoverableProcessing queues are runtime state. Durable analysis markers and generated files prevent unnecessary repetition after restart, while incomplete work can be safely scheduled again.
